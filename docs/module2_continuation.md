## 为Precision增加的策略

固定语义融合使用区域注意力、原标题、机器商品主体/可见外观描述。新约束候选再读取查询文字、商品原标题及机器主体描述，区分商品本体与配件，并检查查询明确要求的无线、袖长、裤长等属性。明确冲突、无法判断、主体匹配但属性不足、主体与明确属性匹配分层排序；层内保留原语义分。

此候选没有读取源类别、查询ID或评审答案作为排序特征，没有删查询、重复商品、缩小K，也没有减少返回数量。图片查询暂不凭空猜商品类型，保持固定语义融合结果。策略是开发可切换候选，没有替换默认行为。

实际“无线蓝牙耳机”探针中，旧固定融合Top10混入耳机保护套；约束候选将前部集中到耳机本体。但尾部仍出现路由器、收纳袋等未知类型商品，部分标题还混有有线/无线属性，说明主体词表覆盖和属性证据仍不充分。这个例子支持继续研究本体/配件混淆，不能证明整体Precision提高或达到60%。

机器弱标签训练仍无可靠的真实质量优势。本轮保留平衡逻辑回归与困难负例RankNet的正负结果，不按机器一致性分数宣称业务达标。内部文件中的机器一致性上下界也不是Precision、置信区间或正式质量成绩。

## 机器复核与数据隔离

固定从旧8种策略的Top30并集中，按最靠前排名和固定种子选择每条查询12对未知关系，共216对；不足时按同一种子补选其余未知关系。没有按复核结果提前停止或补选好结果。

文本查询读取候选原图；图片查询同时读取查询图和候选图，全部使用原标题和原开发相关性规则。图片先按方向转正、缩至最长边512、JPEG质量92。本地Qwen3.5弱监督模型、摘要、提示词、JSON格式、种子和参数在推理前冻结；每条保存原始响应及理由。不确定继续为空，旧1,828条已知机器判断没有覆盖。模型复核看到了开发规则，因此这批判断及其后续交叉验证仍属于开发证据。

两类排序模型沿用3个查询分组×3个商品族分组；每一折排除留出查询组、图库组和图片查询来源族。复核脚本重新训练全部18个分组模型及2个最终候选，核对标准化、权重、预测与排序。未知机器关系不自动转成负例。

300件预留验收商品、30张预留查询图、30个文本席位保持封存；本轮验收候选模型预测为0。读取验收登记和既有指纹仅用于拒绝开发输入，未编码、排序或评分验收候选。运行时拒绝字节、方向校正像素或dHash近重复命中的验收图；登记变化则要求重启核验。旧同款结果完整保留。

## 本地运行与停止

本次服务已启动，可打开[本地检索页面](http://127.0.0.1:8765/)。如果进程已关闭，在项目根目录PowerShell执行：

```powershell
.\.venv312\Scripts\python.exe scripts\serve_retrieval.py --port 8765
```

模型与286件开发索引只在启动时加载一次，每次查询重新做一次嵌入；没有查询结果缓存。默认固定语义融合，其他5个候选须显式选择。服务仅绑定`127.0.0.1`，未设置开机启动，未安装后台服务；运行时嵌入模型继续占用显存。

只停止本项目的检索服务：

```powershell
Invoke-RestMethod -Method Post -Uri 'http://127.0.0.1:8765/api/shutdown' -ContentType 'application/json' -Body '{"shutdown":true}'
```

重启前无需重新下载模型。机器看图复核使用的生成模型已卸载，避免同时占用显存。新增入口不依赖新包、云服务或网络下载。

| 接口 | 用途 |
|---|---|
| `GET /health` | 模型就绪状态、实例ID与计数 |
| `GET /api/samples` | 12条文本、6张开发查询图及策略列表 |
| `POST /api/search` | JSON传入`text`、`image_id`或项目内`image_path`三者之一；图片可附`roi:[x1,y1,x2,y2]`，范围0–1；默认Top10 |
| `GET /media/<固定标识>` | 仅返回已注册开发图片或局部视图 |
| `POST /api/shutdown` | 显式停止当前本地检索服务 |

页面支持指定ROI并裁切放大。结果显示的排序分不是概率或质量指标。请求拒绝未知字段（包括答案类别）、模态混传、无效ROI、外站Origin和预留验收图片；不提供跨站调用。

## 真实性能与浏览器检查

同一常驻实例上执行24个开发输入（12文本、6原图、6相同ROI），各重复2次，共48次顺序HTTP请求；另有预热、五项拒绝检查与图片接口检查。所有请求重新计算嵌入，返回10个唯一商品ID。该混合工作负载轮换6种候选策略，不是各策略均匀的大规模性能验收。

| 项目 | 实测 |
|---|---:|
| 当前实例完整启动及一次预热 | 8.640秒 |
| HTTP整体p50 / p95 / 最大值 | 0.138 / 0.263 / 0.287秒 |
| 文本HTTP p50 / p95 | 0.062 / 0.066秒 |
| 原图HTTP p50 / p95 | 0.222 / 0.246秒 |
| ROI HTTP p50 / p95 | 0.241 / 0.281秒 |

HTTP计时包含输入检查、预处理、查询编码、排序、服务序列化及客户端JSON解析，**不含进程冷启动、浏览器下载图片和页面渲染**。48次均小于5秒只描述本地热态探针；冷启动仍超过5秒，正式端到端性能验收尚未完成。协议、逐请求结果及汇总分别为`service/benchmark_protocol.json`、`benchmark_records.json`、`benchmark.json`。

首次探针暴露Windows对WebP缺少默认MIME类型的问题，页面启用nosniff后图片无法显示。已显式设置JPEG/PNG/WebP响应类型并增加实际HTTP回归测试。失败协议和原执行源码保存在`service/diagnostics/media_type_bug/`；增加主体约束前的成功结果与执行源码保存在`service/source_executed/before_constraints/`。当前新结果独立保存，没有覆盖失败或上一版本耗时。

真实浏览器完成文本约束查询和图片ROI查询，均返回10件商品并显示图片。界面证据：[文本检索](../artifacts/module2_continuation/service/text_constraints.png)、[ROI检索](../artifacts/module2_continuation/service/image_roi.png)。界面单次请求受浏览器与实际时点影响，与48次接口探针数值不同。
